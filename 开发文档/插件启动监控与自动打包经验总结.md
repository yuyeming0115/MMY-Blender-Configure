# 插件启动监控与自动打包经验总结

## 背景

本轮开发围绕插件加载耗时监控、启动探针、手动重测和每周自动打包展开。核心目标是让耗时数据更可信，并减少用户为了测试插件启动速度而反复手动关闭、启用插件的操作成本。

## 问题经验

### 1. 历史耗时不能参与本次统计

旧实现会把 `.mmy_timer_data.json` 中的历史数据直接加载到当前记录列表，并且同名插件保留最长耗时。这会导致旧的高耗时记录长期压住新的真实数据。

处理经验：

- 历史数据只用于临时展示。
- 本次会话数据和历史数据分离。
- 同名插件在本次会话中保留最新结果，而不是最长结果。
- UI 必须提示“历史记录”和“本次记录”的区别。

### 2. 监控插件注入时机天然偏晚

监控插件自身也通过 Blender 插件加载流程启用，因此在它 `register()` 中 monkey-patch 时，部分插件可能已经加载完成。这些插件无法事后得到真实首次加载耗时，只能标记为早期加载。

处理经验：

- 使用 startup 启动探针尽早注入计时逻辑。
- 耗时记录需要标记来源：启动、会话、重测、早期。
- 面板展示时不要把不同来源混成同一种含义。

### 3. 手动重测不等于冷启动

手动重测通过 `disable -> 清理 sys.modules -> enable` 近似测量重新导入和注册成本，但当前 Blender 会话中的全局状态、外部依赖缓存、已加载库仍可能影响结果。

处理经验：

- 手动重测结果标记为“重测”。
- 默认只重测用户选择的单个插件。
- 不允许重测当前监控插件自身。
- 重测下拉列表默认过滤 Blender 内置和官方插件，降低误操作概率。

### 4. 自动打包不能阻塞 Blender UI

Portable 打包可能耗时较长，如果在 Blender 主线程中直接执行，会造成界面卡顿。

处理经验：

- 自动打包只在 timer 中做轻量检查。
- 真正打包交给 `pack_script.py` 子进程执行。
- 使用状态文件记录当前 ISO 周是否已触发，避免周一重复打包。
- 自动打包必须依赖已保存的 Portable 路径和输出目录，空路径不做隐式猜测。

## 后续建议

- 在 Blender 4.5+ 中继续观察启动探针是否覆盖足够早的插件加载阶段。
- 对复杂插件的重测增加二次确认或风险提示。
- 自动打包可后续扩展为可配置星期、可配置检查频率和最近一次打包状态展示。
